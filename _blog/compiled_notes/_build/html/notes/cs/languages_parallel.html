Languages and parallel computing#

Quick references for python, c/c++, java and R, plus how training is split across GPUs.

About this chapter

Most of this chapter is reference material: the python, java and R calls that come up all the time (lists, deques, dicts, string formatting, sorting with a key), and c/c++ details on pointers, references, memory, classes and virtual dispatch. Read whichever language you need; the sections don’t depend on each other.

The GPU section is different in kind. It starts from the point that moving data between GPU memories often costs more than the arithmetic, then describes how training is split across devices: the collective operations (AllReduce, ReduceScatter, AllGather), how DDP and FSDP use them, and the levels of parallelism (data, tensor, pipeline).

Higher level#

Python passes everything by copying a reference. Changing an object through the reference is visible to the caller; rebinding the name inside the function is not.

  • primitives: int, float, bool, str

  • only primitive and reference types

    • when you assign primitives to each other, it’s fine

    • when you pass in a primitive, its value is copied

    • when you pass in an object, its reference is copied

      • you can modify the object through the reference, but can’t change the object’s address

Object-oriented#

A base class can leave a method unimplemented by raising NotImplementedError for subclasses to override. Instance methods get self and can change the object, class methods get only the class, and static methods get neither.

GPU / parallelization#

On a GPU, pointwise operations spend more time moving data from DRAM to SRAM than computing. Fusing several operations into one pass saves those trips, which is why activation functions of very different complexity cost about the same.

  • https://horace.io/brrr_intro.html

    • within gpu, all operations require moving from gpu’s DRAM to GPU’s SRAM

    • for pointwise operations the time to do the moving (memory bandwidth cost) is longer than the computation itself

    • operator fusion allows us to do many operations at once before moving back to DRAM

      • can lead to interesting things, e.g. activation functions are nearly all the same cost, despite gelu obviously consisting of many more operations than relu

Computations#

These are the collective operations used when one model is trained on several GPUs (ranks). DDP keeps a full copy of the model on every GPU and averages gradients with AllReduce. FSDP splits the model itself across GPUs, gathers the pieces before each pass, and scatters the summed gradients afterwards.

  • AllReduce: reduce (e.g. sum) values across ranks = ReduceScatter then AllGather

    • ReduceScatter: reduce some slice across ranks and store it scattered across ranks

    • AllGather: concatenate values across ranks and share copy everywhere

  • DDP – model copied on each GPU (it fits), and calculates loss based on input data batch

    • Works by syncing gradients with Allreduce

  • FSDP – model chunked across GPUs

    • AllGather before each forward pass

    • AllGather before each backward pass

    • Reduce-Scatter gradients after backward (to average them)

Pytorch#

The three levels of splitting a model across GPUs differ in what is split. Data parallelism splits batches and copies the model, tensor parallelism splits parts of an input, and pipeline parallelism puts different layers on different GPUs. The rest lists which pytorch wrapper fits one machine or many.

  • new in 1.11: TorchData, functorch (e.g. vmap), DistributedDataParallel is stable

  • huggingface performance overview

  • overview links from huggingface and pytorch

  • levels of parallelism

    1. DataParallel - split batches across gpus and replicate model on each gpu (model must fit on single gpu)

      • gpt2 & T5 models have naive PP support

    2. TensorParallel - split parts of an input across gpus

      • parallelformers provides easy support for inference-only

    3. PipelineParallel - split different layers across gpus

      • naive - diff layers on diff gpus (increases mem but not speed)

      • pipeline parallel - separates so more gpus can work at once

      • Deepspeed/Megatron/Varuna/Sagemaker combine dataparallel with pipeline parallel

  • pytorch parallel overview

    • single-machine multi-GPU: DataParallel - relatively simple

      • just wrap model model = nn.DataParallel(model) (some attributes may become inaccessible)

    • single-machine multi-GPU: DistributedDataParallel - slightly faster

      • requires also calling init_process_group (and setting some env vars)

    • multimachine GPU: DistributedDataParallel + launching script

    • multimachine flexible: torch.distributed.elastic - handles errors better

    • (there is also RPC-based training and Collective Communication)

  • dataset has __init__, __getitem__, & __len__

    • rather than storing images, can load image from filename in __getitem__

  • there’s a torch.nn.Flatten module

Parallelization#

Vocabulary first: cores within a node, nodes with separate memory, processes, and threads inside a process. Libraries like dask and ray handle the message passing between nodes so the code doesn’t have to.

  • cores = cpus = processors - individual processing units available on a single node

  • node - different computers with distinct memory

  • processes - instances of a program executing on a machine

    • shouldn’t have more user processes than cores on a node

    • threads - multiple paths of execution within a single process

      • like a process, but more lightweight

  • passing messages between nodes (e.g. for distributed memory) often use protocol known as MPI

    • packages such as Dask do this for you, without MPI

  • python packages

    • dask: parallelizing tasks, distributed datasets, one or more machines

    • ray: parallelizing tasks, building distributed applications, one or more machines

  • dask

    • separate code from parallelization

    • some limitations on pure python code, but np/pandas etc. parallelize better

    • configuration: specify sequential (‘synchronous’), threads within current session (‘threaded’) parallel (‘processes’) multiprocessing - this creates copies of objects, multi-node or not (‘distributed’)

    • need to wrap functions with delayed() or map()

      • alternatively can tag functions

    • map() operation does caching

    • dask dataframes

    • ssh setup

      • can connect to other workers locally (ssh-dask or SSHCluster)

      • when using slurm, must run dask-scheduler on cluster node

        • then run dask-worker many times (as many tasks as there are)

      • can also directly submit slurm jobs from dask

Filetypes#

Parquet stores a table by column instead of by row, so a query reads only the columns it needs and each column compresses well.

Apache Parquet - an open-source, column-oriented data file format designed for efficient data storage and high-performance retrieval in big data analytics. Unlike row-based formats (like CSV), Parquet stores data by column, allowing for better compression and faster analytical queries by only reading necessary columns

Malloc#

malloc returns a void * to fresh heap memory that has to be cast, and every block must be freed exactly once. A string literal, by contrast, points into read-only memory.

  • malloc ex.

  • There is no bool keyword in C

  int *foo;
  /* malloc call: note the cast of the return value
     from a void * to the appropriate pointer type */
  foo = (int *) malloc(sizeof(int));  
  *foo = 5;
   free(foo);

  • char *some_memory = "Hello World";

  • this creates a pointer to a read-only part of memory

Virtual method tables - stores the virtual methods in an array
    Each object contains a pointer to the virtual method table
        In addition to any other fields
    That table has the addresses of the methods
        Any virtual method must follow the pointer to the object... (one pointer dereference)
        Then follow the virtual method table pointer... (second pointer dereference)
        Then lookup the method pointer
            In Java default is Dynamic
            In C++, default is Static - this is faster
    When creating a subclass object, the constructor of each subclass overwrites the appropriate pointers in the virtual method table with the overridden method pointers

Key ideas

  • Python and java pass objects by copying a reference, so a function can change an object but not rebind the caller’s variable.

  • Python’s x.copy() is shallow; nested objects need deepcopy.

  • {‘In C you manage memory yourself’: “locals on the stack, globals in a data segment, and malloc’d memory on the heap until it is freed.”}

  • C++ dispatches statically by default and only looks up the run-time type for virtual methods, through a table of method pointers; java makes every method virtual.

  • On a GPU, moving data between memories often costs more than the arithmetic, which is why fusing operations helps.

  • AllReduce is ReduceScatter followed by AllGather; DDP uses it to average gradients, and FSDP gathers model shards before each pass and reduce-scatters the gradients after.
